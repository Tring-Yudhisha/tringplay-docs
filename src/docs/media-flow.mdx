## Menu

The **menu** is the main navigation (e.g. sidebar or top bar). The JW Config response includes a **menu** array; the app uses it for navigation items **other than** Home. The app **internally adds** a **Home** menu item (and optionally **Search**) so that the full menu is: [Search (if enabled), **Home**, …menu items from JW Config]. When the user selects **Home**, the app shows the **Home screen** (the landing page driven by the **content** array). Other menu items (e.g. Leagues, Live, Hub) come from the **menu** array and load their own content. So: **Menu** = list of nav entries (Home is app-added; the rest come from JW **menu**); **Home screen** = the view when the user selects Home = **content** (landing page).

Each **menu** array item from JW Config has:
- **contentId:** ID used to load the content (playlist, media, watchlist).
- **label:** Text shown in the navigation (e.g. "Leagues", "Live").
- **type:** Usually playlist or media; tells the app how to load the item.
- **filterTags** (optional): Used to filter content.
- **custom** (optional): Extra config for the item.

The app builds the displayed menu by prepending **Home** (contentId: "home", label: "Home", type: "home") and optionally **Search**, then appending the **menu** array from JW Config. When the user selects **Home**, the app shows the Home screen (landing page from **content**). When the user selects another item, the app loads that item’s playlist or content.

Example **menu** array as returned by JW Config (this does not include Home; the app adds Home internally):

```json
"menu": [
  {
    "contentId": "2gNQCcXt",
    "custom": {},
    "filterTags": "",
    "label": "Leagues ",
    "type": "playlist"
  },
  {
    "contentId": "cKLiHMnf",
    "custom": {},
    "filterTags": "live-event",
    "label": "Live ",
    "type": "playlist"
  }
]
```

The app displays: **Home** (app-added) first, then **Leagues**, then **Live**. Selecting **Home** shows the Home screen (landing page). Selecting **Leagues** or **Live** loads the corresponding playlist.

## Home Screen

The **Home screen** is the landing view that appears when the user selects the **Home** menu item (see Menu above). It is driven by the **content** array in the JW Config response: each item in **content** defines a row or section on the landing page (featured section, playlists, Favorites, Continue Watching, etc.). So the flow is: **Menu** → user selects **Home** → app shows **Home screen** → Home screen renders the **content** (featured + rows).

### Featured Section

On the landing page, the rows (carousels and shelves) come from the app config response under the key content. Each item in content has contentId, title, type (e.g. playlist, favorites, continue_watching), featured, filterTags, and optional custom and enableText.

For items with type playlist, the app calls the playlist API using the contentId to load the playlist. If an item has featured: true, it is shown in the featured section (typically rendered as one large carousel at the top). All other items are shown as rows below in the order they appear in content. Items with type favorites or continue_watching use the features list IDs from the config and their own APIs (see Favorites and Continue Watching below).

### Playlist Content

For each content or menu item with type playlist, the app loads the playlist by calling this API with the item’s contentId as playlist_id. The response is the playlist metadata and an array of media items (title, mediaid, image, sources, etc.) used to render the row or carousel. Pagination is supported via query params page_limit and page_offset; the response includes links (first, last, next) for paged requests.

**Request URL:** `https://cdn.jwplayer.com/v2/playlists/{playlist_id}`
**Method:** `GET`
**Payload:**

"playlist_id" : "xaCDDmsj"

### Hub

**Hub** is one of the **content types** of media (like movie, series). The flow is: **Details screen** → app calls the **Media Details** API for the selected media_id → response has `contentType: "hub"` and a **playlist** field (comma-separated playlist IDs) → app then calls the **playlist API** for each ID and renders each result as a row/section on the hub page.

**Step 1 — Media Details (same as Media Details above):**

**Request:** `https://cdn.jwplayer.com/v2/media/{media_id}`  
**Method:** `GET`
**Payload**
```
media_id = "JYembQOG"
```

**Response:** The response has kind: "Single Item" and a playlist array. The first item (playlist[0]) contains contentType: "hub" and playlist: "Mye5LqB6,siqAG29Y" (comma-separated playlist IDs). The app uses this to determine it is a hub and which playlists to load.

**Example response (abbreviated):**
```json
{
  "title": "Hub Test 3",
  "description": "This is a test description to display the description for Hub...",
  "kind": "Single Item",
  "playlist": [
    {
      "title": "Hub Test 3",
      "mediaid": "JYembQOG",
      "image": "https://cdn.jwplayer.com/v2/media/JYembQOG/poster.jpg?width=720",
      "contentType": "hub",
      "playlist": "Mye5LqB6,siqAG29Y",
      "description": "...",
      "sources": [{ "file": "None", "type": "application/octet-stream" }],
      "variations": {}
    }
  ],
  "feed_instance_id": "f8929107-fb7e-497f-87e1-a2177831588d"
}
```

**Step 2 — Call playlist API for each ID:**

Based on `playlist: "Mye5LqB6,siqAG29Y"` the app calls the playlist endpoint for each ID:

- `GET https://cdn.jwplayer.com/v2/playlists/Mye5LqB6` 
- `GET https://cdn.jwplayer.com/v2/playlists/siqAG29Y` (e.g. with ?page_offset=1&page_limit=5 for pagination)

Each response returns a playlist (title, playlist array of media items). The app renders each as a section/row on the hub details page (e.g. "Movies", "Series Content").

## Access

Before playing protected content, the app checks whether the user has access (Content Access Check). If access is granted and the content is DRM-protected, the app requests a DRM token and then uses the JW Player DRM playback URL with that token. The base URL for these calls can be customized (e.g. per deployment).

### How DRM works

1. **Access check (InPlayer)** — When the user tries to play, the app calls the Content Access endpoint. That answers whether the user is allowed to play this product. If not, the app shows a paywall and does not continue.
2. **DRM token (InPlayer)** — If access is granted and the content is DRM-protected, the app requests a short-lived token from the auth backend (app_config_id, media_id). That token proves to JW Player that this user may get DRM playback for this media.
3. **JW Player DRM URL (Delivery API)** — The app calls the JW Delivery API with the token.
```
GET https://cdn.jwplayer.com/v2/media/{mediaId}/drm/{drmPolicyId}?token={token}
```


**Payload**
```
mediaId = "VV8Vy1Zi"
drmPolicyId = "iKZNk91d"
token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJjcmVhdG9yIjoiaW5wbGF5ZXIiLCJleHAiOjE3NzQ1MzMwMDAsInJlc291cmNlIjoiL3YyL21lZGlhL1ZWOFZ5MVppL2RybS9pS1pOazkxZCJ9.cXmtgf2cIxr2H2LbuVfrI-Awce4RB2SSwhH1esWq3h8"
```
JW returns playback JSON (metadata, manifest URLs, license acquisition URLs). The player uses this to decrypt and play. For DRM, JW requires the request to be signed (the token does this); returned media and license URLs are time-limited (e.g. valid for about 10 minutes). For playlists of DRM content, JW exposes a playlist endpoint that returns the same kind of signed, time-limited data for multiple items. See [JW Player DRM Playlist objects](https://docs.jwplayer.com/platform/reference/get_v2-playlists-playlist-id-drm-policy-id).


**SSAI + DRM:** When server-side ad insertion (SSAI) is enabled with DRM, the app may use the playback endpoint instead
```
GET https://cdn.jwplayer.com/v2/sites/{siteId}/media/{mediaId}/playback.json?token={token}&drm_policy_id={drm_policy_id}&ad_config_id={ad_config_id}
```
```
siteId = "z1RVAXZN"
mediaId = "VV8Vy1Zi"
token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJyZXNvdXJjZSI6Ii92Mi9zaXRlcy96MVJWQVhaTi9tZWRpYS9WVjhWeTFaaS9wbGF5YmFjay5qc29uIiwiZHJtX3BvbGljeV9pZCI6ImlLWk5rOTFkIiwiYWRfY29uZmlnX2lkIjoieklFNDVRQjIiLCJleHAiOjE3NzQ1MjM0MDB9.0bX2A3EaVRIcE-mbMtPRSYL10RXfsuudpmkqeS29nv4"

```
 with query params token, drm_policy_id, and ad_config_id. The response includes signed playback and ad configuration.

### Content Access Check

The app calls this when the user tries to play a media item that is tied to a product (subscription or one-off). productId is the item’s product ID (e.g. from the media’s productIds or productIdsStaging in the playlist/details response). If the response indicates access, the app can proceed to request a DRM token (for protected streams) or load the standard playback URL.

**Request URL:** `GET https://services.inplayer.com/items/{productId}/access`
**Headers:** `Authorization: Bearer <access_token>`

**Response:**
```json
{
  "access": true,
  "expires_at": 1760000000
}
```

access is true when the user is entitled to the product; expires_at is a Unix timestamp when that access ends. If access is false or the call fails, the app typically shows a paywall or upgrade message instead of playing.

### DRM Token

For DRM-protected streams, the app gets a token from the auth backend before calling the JW Player DRM playback URL. media_id is the ID of the media being played; app_config_id comes from app config (e.g. drmConfigId).

**Endpoint:** `POST https://services.inplayer.com/v2/items/jw-media/token`

**Payload:**
```json
{
  "app_config_id":"ffuxvbfv",
  "media_id": "hkJH3ic1"
}
```
**Headers:** `Authorization: Bearer <access_token>`

**Response:**
```json
{
  "token": "drm_token_value",
  "expires_at": 1760000000
}
```

**Notes:** Mandatory for secure streams. The app passes the token to the JW Delivery API (e.g. .../v2/media/&#123;mediaId&#125;/drm/&#123;drmPolicyId&#125;?token=...) so the stream can be decrypted. Without a valid token, DRM playback will not start. On some platforms the request may be made via an auth SDK that calls this backend.
